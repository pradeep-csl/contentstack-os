# Contentstack (Venus) design system — UI re-skin

**Date:** 2026-08-06
**Status:** Design approved, pending spec review
**Scope:** Token-level re-skin of all three UI surfaces. No component rewrites.

## Problem

The UI is a fork of Cloudflare's Gadgets Workshop and still looks like it: warm near-neutral
greys, a `#ff4801` orange accent, and the product name "Cloudflare OS". It needs to read as a
Contentstack product.

Contentstack's design system is **Venus**, published as `@contentstack/venus-components`. Its
token set (`build/variables.css`, generated by Style Dictionary) is the authority for every value
in this document.

## Approach

Re-target the token layer that already exists. The frontend styles the Kumo component library
through Tailwind v4 `@theme` variables plus Kumo semantic-token overrides, so a palette change is
a change to a small number of CSS custom properties rather than to components.

`@contentstack/venus-components` is **deliberately not installed**. It is 14.1 MB across 1457
files with ~60 runtime dependencies (`lodash`, `moment`, `axios`, `recharts`, `slate`,
`react-beautiful-dnd`, `react-dnd-11`, `react-redux`, `systemjs`) and would replace a lean Vite
SPA's dependency graph to obtain values we can read from its stylesheet. We treat its
`variables.css` as a specification, not as a dependency.

### In scope

Color (light and dark), corner radius, elevation, Monaco editor theme, product identity, and a
shared token file so the three surfaces stop diverging.

### Explicitly out of scope

| Excluded | Reason |
|---|---|
| Component code | No `.tsx` restructuring, no Kumo import changes. |
| `@contentstack/venus-components` dependency | See above. |
| Font family | Deferred by decision — to be discussed separately. The stack stays as-is. |
| Type scale | Reflows layout across ~45k LOC; deferred by decision. |
| Tailwind `--spacing` base | Same; the 4px base stays. Venus's 2px scale is not adopted. |
| Third-party vendor brand colors | Slack `#4A154B`, Google `#4285F4`, Discord `#5865F2`, Jira `#0052CC`, GitHub `#24292e` and similar are correct as-is; re-tinting them would be a defect. |

The type-scale and spacing exclusions are worth restating because the original request mentioned
spacing. They were excluded after the layout-reflow cost was presented. Venus's spacing and type
scales remain available for a later pass.

## Decisions

|---|---|

### Assumptions requiring confirmation

- **A1 — Logo asset. RESOLVED.** The Contentstack "stack" mark was supplied as a 256×256 RGBA
  PNG, dominant colour `#7c4dff`, source:
  `https://messenger-assets.qualified.com/uploads/7U2CPoFU4R81E3E5PtMJJkxs7HjjQ8xSJ2bYV/19c20494b0ccfdc03de871a3a441460fa5f0b9e1fdcd40e037058eddcb07347c.png`
  The raster has since been **vectorised** to
  `packages/workshop-frontend/public/contentstack-logo.svg` (871 bytes, 12 capsule `<rect>`s on a
  256 viewBox). The mark is 15px bars on a 20px grid with exact 180° rotational symmetry about the
  centre, so it traces exactly rather than approximately; the trace was verified by rasterising and
  confirming the bounding box matches the original under a single uniform scale with zero
  translation. Because an SVG is available, `index.html` keeps `type="image/svg+xml"` and there is
  no HiDPI concern for the top bar.

  The SVG is filled `#7C4DFF` — the mark's true colour. Per **A4** the brand *token* is `#6c5ce7`,
  so the two differ by design; if the logo should instead track the brand token, change the single
  `<g fill>` or set it to `currentColor` for CSS-driven tinting in the app (a favicon still needs a
  literal fill).

  `favicon.svg` is **not** yet replaced — that is an implementation step, not part of this spec.
- **A2 — Spec location. RESOLVED.** Specs stay in `docs/superpowers/`, accepted as untracked.
- **A4 — Brand purple. RESOLVED: `#6c5ce7`.** The supplied logo is `#7c4dff`, a visibly different
  purple, and `variables.css` in `@contentstack/venus-components@3.0.5` is stamped
  `Generated on Fri, 14 Jul 2023`, so the package may lag the current brand. The decision is to
  follow Venus. Consequence to accept knowingly: the mark and the brand token will not match
  exactly where they appear together, most visibly the top bar. If that reads badly in the
  manual walkthrough, the cheapest fix is recolouring the mark to `#6c5ce7` for in-product use —
  which is a brand call, not an implementation one, so it is not assumed here.
- **A3 — Radius depth. RESOLVED: adopt the full Venus ramp.** The earlier caution conflated radius
  with the type/spacing exclusions, which is wrong: radius changes no geometry, so it cannot
  reflow layout — it is purely visual and revertable per token. Usage counts confirm the change
  is safe: `rounded-lg` 143, `rounded-full` 111, `rounded-xl` 110, `rounded-md` 101, `rounded-2xl`
  51, and **`rounded-sm` is unused**. Pill and circular shapes use `rounded-full`, which Tailwind
  fixes at `9999px` independently of these tokens, so nothing that should stay a pill is at risk.
  Half-adopting would leave the product Contentstack-coloured but Cloudflare-shaped, and corner
  radius is among the strongest signals of which design system a UI belongs to.

**Three deliberate deviations from verbatim Venus, all for contrast:**

0. `--color-kumo-line` is a **translucent** `#4751611f`, not the solid `#dde3ee` first proposed.
   A solid `#dde3ee` line is invisible on the `recessed` and `fill-hover` surfaces, which are
   *also* `#dde3ee` — a 1.00:1 ratio, i.e. borders silently disappear wherever those surfaces are
   used. The token being replaced (`#1411100f`) is translucent for exactly this reason, and the
   replacement preserves that property at Venus's `font-base` hue. `--color-kumo-ring` stays
   solid `#c7d0e1`, since a focus ring must not compose with what is behind it.


1. `--text-color-kumo-warning` uses `#704b00` (`brand-attention-dark`) rather than `#ffae0a`.
   Amber at `#ffae0a` on white is roughly 1.9:1 and fails WCAG AA as body text. Venus provides
   `-dark` variants for exactly this purpose.
2. `--color-kumo-info-tint` is `#eef5fe`, not Venus's `brand-info-light` `#f5fdff`. Venus's info
   *light* is hue-matched to its cyan `brand-info-base` `#00b9e0`, but we use the readable
   `#0469e3` aqua for the info base, so the pale companion is re-derived at that hue.

### Preserving the admin accent override

The first draft of this spec said the dark brand fill should become "the seed itself". That is a
**regression** and must not be implemented as written.

`accentVars()` currently derives the dark fill as `oklch(from ${seed} 0.45 c h)`. Pinning
lightness to `0.45` is what makes an arbitrary admin-chosen accent safe in dark mode: a deployment
that picks a pale seed (yellow, mint, light blue) still gets a button dark enough for white
label text. Substituting the raw seed removes that guard and produces unreadable buttons for
every deployment that overrides the accent — a feature the spec elsewhere promises to preserve.

The fix is to widen the guard rather than delete it, clamping instead of pinning, so that a seed
already in the safe band passes through unchanged while a pale seed is still darkened:

```
oklch(from ${seed} clamp(0.38, l, 0.60) c h)
```

Contentstack purple sits at L ≈ 0.55 and so survives intact, satisfying D5, while the failure mode
for custom accents stays closed. The exact upper bound should be confirmed against white label
text during implementation.

### Why a shared token package

The three files are already 828, 451 and 79 lines, and the scheduler carries only a subset of the
tokens — they have drifted once and will drift again if re-skinned in triplicate. One `tokens.css`
imported by all three makes this a single edit now and in future.

Tailwind v4 resolves `@import` through Vite, so `@import "@gadgets/design-tokens/tokens.css"`
works given a workspace dependency and an `exports` map. **Risk:** if package-specifier resolution
misbehaves under `@tailwindcss/vite`, fall back to a relative import
(`@import "../../design-tokens/tokens.css"`), which is uglier but reliable. This fallback is
acceptable and should not block the extraction.

Each surface keeps its own `@source` and `@import "@cloudflare/kumo/styles"` lines; only the token
blocks are shared.

## Measured contrast

Dark was verified when the palette was chosen. Light has now been measured too, against WCAG AA
(4.5:1 body text, 3:1 large text and UI):

| Pair | Ratio | |
|---|---|---|
| `#475161` default on `#ffffff` / `#f7f9fc` | 8.02 / 7.61 | pass |
| `#647696` subtle on `#ffffff` | 4.59 | pass, narrowly |
| `#647696` subtle on `#edf1f7` tint | 4.05 | **large/UI only** |
| `#a9b6cb` inactive on `#ffffff` | 2.05 | **fails as body text** |
| `#6c5ce7` brand on white / white on brand | 4.86 | pass |
| `#7c4dff` logo purple, same pairs | 4.81 | pass |
| `#007a52` / `#d62400` / `#0469e3` on white | 5.38 / 5.11 / 5.08 | pass |
| `#704b00` warning text on white | 7.79 | pass |
| `#ffae0a` attention **as text** | 1.86 | **fails** — hence deviation 2 |

Two items to handle rather than ignore:

- **`#647696` on tinted surfaces (4.05).** Acceptable for labels and UI text, not for paragraphs.
  Implementation should not place body copy in `subtle` on a `tint` background; where that
  combination exists today, the text moves to `default`.
- **`#a9b6cb` inactive (2.05).** This is Venus's own `font-tertiary`. WCAG exempts genuinely
  disabled controls, and the token being replaced (`oklch(66% 0.005 60)`) fails by the same
  margin, so this is neither a regression nor a Venus misreading. It becomes a defect only if the
  token is used for placeholder text or timestamps rather than disabled state — worth an audit
  during implementation, but out of scope to fix globally here.

## Testing

Token changes are not unit-testable, but they are very capable of producing unreadable text, so
verification is deliberately empirical.

1. `pnpm lint` (oxlint + recursive `tsc --noEmit`) and `pnpm test` per touched package. The
   existing `X-Title` test must be updated and passing, not skipped.
2. Build all three surfaces to confirm the shared-token import resolves under
   `@tailwindcss/vite` — the one genuine technical risk in this design.
3. Manual walkthrough in **both** modes across: home/prompt, chat, gadget editor (Monaco), gadget
   use view, admin, connections, blueprints, login/signup, and the two gatekeeper apps. Confirm no
   warm-orange survives and no text falls below AA.
4. Confirm the admin accent picker still overrides the default and that clearing it restores
   `#6c5ce7`.

Split into reviewable commits, per `AGENTS.md`'s preference for keeping kernel changes separate
from UI:
